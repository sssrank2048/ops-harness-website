# ADR 0018：指标知识库元数据目录与配套技能文件

- 状态：接受（2026-09-18，运营侧需要在云端集中维护指标知识库元数据，办公助手刷新知识中心即可看到）。
- 与 ADR 0013 的管理后台、ADR 0015 的内容目录并列；不改变发布、更新协议与内容同步，公开只读接口保持匿名。

## 背景

指标知识库的租户、检索工作流 ID、知识库 ID、描述与覆盖范围原先散落在各端配置里，新增或调整租户需要改产品代码或逐台改配置。运营希望在官网后台集中维护，并为每个知识库配一个技能文件；所有装了办公助手的用户刷新知识中心即可看到最新目录，绑定后该知识库与技能进入数据分析专家。

官网只拥有官网页面、文档、管理后台与发布存储，不启动 DSH、不读取用户会话。因此这里只承担两件事：管理员维护的元数据，以及按内容哈希保存并分发的技能文件字节。租户鉴权、绑定事务与技能安装都在端侧完成。

## 决策

**元数据落在内容目录，不进数据库、不进 Git。** `<contentDirectory>/knowledge/catalog.json` 保存 `{ schemaVersion, updatedAt, items }`，沿用 `withLock` + 同目录临时文件 + rename 的既有写入方式，覆盖或删除前把旧目录复制到 `.trash/catalog-<时间戳>.json`。`revision` 是规范化后内容的 SHA-256，不写进文件本身避免自引用；所有写接口携带当前 `revision`，不一致返回 `409 REVISION_CONFLICT`。`id` 创建后不可修改、`tenant_id` 目录内唯一，条目上限 500。

**技能文件按内容哈希不可覆盖地保存。** 上传复用发布包用的 `receiveFile`：边接收边落临时文件，校验通过后 rename 为 `skills/<sha256>.<zip|md>`；已存在同哈希文件直接复用。删除条目时文件保留，因为多个条目可以引用同一份技能；无引用文件的清理留到后续的同步/清理动作。

**ZIP 只做字节级结构校验，不解压到磁盘、不执行内容。** 用 `node:zlib` 的 `inflateRawSync` 写了一个最小中央目录读取器，只接受 stored 与 deflate，拒绝 zip64、加密、多卷、缺长度的数据描述符、重复条目名、绝对路径、`..`、反斜杠、符号链接位，以及超过 256 个条目或解压后超过 20 MiB；解压前按声明长度限流，解压后核对长度与 CRC-32。只有 `SKILL.md` 一个条目会被真正解压，其余文件视为技能附属资源、原样保存在压缩包内。压缩包必须恰好含一个 `SKILL.md`，位于根或唯一的一级目录内，位于目录中时目录名必须等于 frontmatter 的 `name`；frontmatter 用已锁定的 `yaml` 包按 `uniqueKeys` 且禁用别名解析，要求小写连字符格式的 `name` 与非空 `description`。不引入压缩库，不新增依赖。

**公开接口匿名只读，两个地址的缓存语义不同。** `GET /api/knowledge/metrics` 只返回上架条目，`Cache-Control: no-store` 配 `ETag: "<revision>"`，端侧带 `If-None-Match` 刷新时命中返回 304，避免每次刷新都传整份目录。`GET /api/knowledge/metrics/skill` 的地址由可变的 `id` 构成——同一个 `id` 的技能文件可以被替换——所以这里同样用 `no-store` + `ETag: "<sha256>"`，靠内容哈希复用字节，替换后客户端立即拿到新内容，而不是用 `immutable` 把旧文件钉在缓存里。响应另带 `X-Skill-Name` 与 `X-Skill-Sha256`，端侧下载后可直接比对。

**字段名保持产品侧给定的 snake_case。** 数据工作流键名为 `query_card_data`（2026-09-19 更正，早期误写为 `quer_card_data`，服务端读取时兼容旧键）。 这就是两端共享的 JSON 契约，类型与上限写在 `shared/knowledge.ts`，两端各自校验。本期不引入跨仓库 vendor 契约包，等端侧实现稳定后再评估。

**管理界面沿用现有后台。** `/admin` 增加“知识库”页签，结构与发布包管理一致：左侧条目列表（租户名、`id`、上架状态、是否已配技能），右侧表单与技能文件区，删除与移除用应用内确认框，未保存修改有离开确认。走既有的密码会话、Host/Origin、CSRF 与 revision 校验，不新增账号体系或 API Token。

## 结果

运营改一次官网即可覆盖全部安装，端侧不再为新增租户改配置。公开接口无凭据、无用户数据，可以直接匿名读取；`If-None-Match` 让刷新的常态成本接近零。

代价是官网多了一段自研的 ZIP 解析代码。它只读中央目录、只解压一个条目、全程有条目数和体积上限，且失败一律回到 `INVALID_SKILL_FILE`，但仍需要在后续变更中保持这些边界。技能文件按哈希留存，删除条目不回收磁盘，需要在运维手册里交代备份与容量。

官网不校验技能内容的可用性，也不验证 `tenant_id` 在 DataAgent 中是否存在——那是端侧绑定时的两层鉴权要做的事。目录里的条目只代表“运营已登记”，不代表当前账号有权访问。

## 验证

`test/knowledge.test.ts` 覆盖目录 CRUD、revision 冲突、字段与标识校验、租户唯一、公开目录只含上架条目并响应 304、技能 ZIP（一级目录内、根目录、`../` 穿越、缺失 / 重复 `SKILL.md`、目录名与 `name` 不符、多个一级目录、超深路径）与 `.md` 校验、超限 413 与非二进制 415、公开下载的字节与响应头、替换技能后旧 `ETag` 失效、删除后 404，以及新增管理路由的匿名 / 跨域 / 缺 CSRF 拒绝与重启后读取一致。UI 修改需在真实浏览器验收新建、上传、上下架与页面切换。

## 2026-09-19 修订：技能文件改为目录级公共配置

运营侧反馈配套技能不是每个知识库各一份，而是所有指标知识库共用的一份。因此 `catalog.json` 顶层新增 `skill`，条目不再携带
`skill`（旧文件里的条目级 `skill` 读取时忽略，下一次写入即消失）；管理接口改为 `POST/DELETE /api/admin/knowledge/skill`，
公开下载改为 `GET /api/knowledge/metrics/skill`，缓存语义不变（`no-store` + `ETag: "<sha256>"`）。管理页面把技能上传放到
条目列表之上，“技能名全目录唯一”的规则随之取消。端侧绑定第一个知识库时安装该技能，绑定更多知识库不重复安装，
解除最后一个绑定时移除。

## 2026-10-09 修订：多技能引用与自定义工作流

运营需要维护多个可复用技能，并为每个知识库单独选择引用；检索工作流也需要按实际接口填写名称和值，不再限定三个输入框。本修订取代前述单一共用技能与固定工作流字段的当前契约，保留历史决策供迁移时参考。

**目录升级到 v2。** 持久化结构为 `{ schemaVersion: 2, updatedAt, skills, items }`，管理和公开响应另含派生的 `revision`。`skills` 是最多 100 个名称唯一的技能元数据组成的数组；每个条目用 `skill_names: string[]` 引用零个或多个已上传技能，同一技能可以被多个条目引用。不存在的名称或重复引用拒绝保存。条目仍以 `id` 标识，租户、知识库 ID、描述与上架规则不变。

**按技能名上传、替换和删除。** `POST /api/admin/knowledge/skills?name=<文件名>` 以 frontmatter 的 `name` 作为技能标识：未登记的名称新增，已登记的名称替换文件并保留所有知识库引用。查询参数仍只是原始文件名，不决定技能名。`DELETE /api/admin/knowledge/skills/:name` 仅移除未被任何知识库引用的技能；包括下架条目在内的引用返回 `409 SKILL_IN_USE`，不自动修改知识库。单文件 5 MiB、ZIP 结构校验、哈希存储及 revision / CSRF / 锁 / 原子写入规则保持不变，移除不清理哈希文件。

**工作流改为字符串映射。** `knowledge_retrieve_workflow_id` 接受 `Record<string, string>`，允许空对象、最多 50 项，名称最多 80 字符、值最多 256 字符；名称和值去除首尾空白后不能为空。名称规范化后必须唯一，并拒绝 `__proto__`、`constructor`、`prototype`，避免特殊对象键进入配置。管理页面逐行编辑“名称 / 值”，支持新增和删除行，不预设必须填写的工作流。

**旧数据读取时迁移，成功写入后落盘。** v1 顶层 `skill` 转成单元素 `skills`；已有条目未声明 `skill_names` 时默认引用该技能，没有顶层技能时默认空引用。显式已有的 `skill_names`（包括 `[]`）保留，旧条目级 `skill` 继续忽略。仅 v1 迁移将 `quer_card_data` 归一为 `query_card_data`，两者同时存在时保留后者；v2 名称不再执行该别名转换。读取不改写旧文件，首次成功写入前将原 v1 目录备份至 `.trash/catalog-<时间戳>.json`，再保存 v2；新建知识库或新增技能也执行该首次备份。revision 基于规范化后的 v2 内容生成，升级前页面持有的旧 revision 需要重新获取。

**公开契约需要产品端协同升级。** `GET /api/knowledge/metrics` 返回 `schemaVersion: 2`，包含完整技能列表及已上架条目的 `skill_names` 与工作流映射；`GET /api/knowledge/metrics/skills/:name` 下载指定技能，包括尚未被引用的已上传技能。缓存仍为 `no-store`，目录 ETag 使用 revision，技能 ETag 使用 SHA-256。产品端需要识别 v2、按各知识库引用解析技能，并明确多个绑定共用技能时的安装和移除规则。本仓库不包含或验证产品端绑定、安装实现，存储迁移不代表旧客户端已兼容。

旧 `POST /api/admin/knowledge/skill` 保留为上传别名；旧单数下载和删除只在恰好一个技能时使用，零个返回 `404 SKILL_NOT_FOUND`、多个返回 `409 SKILL_NAME_REQUIRED`，删除仍受引用检查约束。该兼容入口不将 v2 目录降级回单技能契约。

本修订的验证范围包括多技能上传和同名替换、引用保存及在用删除拒绝、v1 迁移与重启读取、任意工作流名称/值及边界校验、公开 v2 目录和指定技能下载。管理页面还需在真实浏览器验收多文件选择、引用选择、工作流行增删、未保存修改、键盘操作和窄屏布局；具体执行结果记录在本次交付中，不由此决策文档宣告测试完成。

## 2026-10-10 修订：每库单技能与旧客户端持续兼容

本修订取代 2026-10-09 的公开 v2 原地址与多引用决策。中间客户端改动只推送代码、尚未发包，已发客户端继续使用旧地址及旧响应。

- 一份当前配置，双协议响应；不冻结旧目录，不增加独立旧版编辑或发布流程。
- 平台 `skills[]` 保存多个技能，每库 `skill_name: string | null` 引用一个技能。旧 v1 顶层技能自动进入技能池并被全部旧库引用，工作流 key/value 和身份信息保持；旧拼写仅迁移无冲突的别名。冲突原值保留，旧响应排除此条目并在管理员页提示。
- 持久 `legacy_skill_name` 表示原公共技能身份，始终读取该身份的当前文件，新增或排序技能不改变它。未发版数组配置无身份时从有效 v1 备份恢复，否则管理员一次性明确选择；原来无技能为 null，未知为字段缺失，两者不能混淆。未知时 v1 暂不可用，v2 不受影响。
- 内部 `skill_names` 零项/一项自动转为 null/名称，多项保存在 `pending_skill_names` 并显示选择提示，保存选择前不发布该条目。原目录首次写入前备份，绝不静默取第一项。
- 原 `/api/knowledge/metrics` 从当前已上架库中选择固定三个工作流齐全且引用原公共技能的库，返回 v1、顶层单技能、旧条目字段与同值 query/quer 别名；新增的兼容库也纳入。`/skill` 精确定位原公共技能，不再因技能池多于一个而 409。
- `/api/knowledge/metrics/v2` 返回完整映射及单技能引用；`/v2/skills/:name/:sha256` 校验名称和哈希并读取不可变历史文件。同名替换不会使已接收的 v2 清单下载到不同字节。
- 两表示的 ETag 独立，旧目录 2 MiB、新目录 96 MiB；写入前拒绝超出旧响应限制的配置，保持原文件不变。更改配置后两端读取同一份当前数据，客户端仍自行决定何时同步已绑定快照。
- 新增/改名方法 key 限 1–64 位字母数字下划线连字符并拒绝 run_code 和特殊对象键；历史无效名称可读取和原名保存，UI 提示修正，不自动改名或丢值。

沿用认证、CSRF、revision、独占锁、备份和原子写。技能池保持多文件上传，各库用 radio 单选。原公共技能身份视为引用，防止误删，更新通过同名上传。旧下载协议不含预期哈希，无法消除目录读取与同名上传间的既有竞态；保留原客户端哈希校验/刷新重试。

验证包含真实 HTTP v1/v2、迁移重启、实时修改、原技能身份、多个技能、未发布多引用保留、不可变下载、历史方法名与新名称约束、独立 ETag、公开大小边界。真实旧客户端和新版 Host 的端到端结果由产品仓库联调记录承担。
